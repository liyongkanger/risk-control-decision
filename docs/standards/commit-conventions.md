# Git 提交规范

状态：已确认的项目约定。适用于本规范生效后的新提交；已推送的历史提交保持不变。

## 1. 提交标题

统一使用以下格式：

```text
<type>(<scope>): <中文动作和结果>
```

- `type` 使用小写英文；`scope` 使用小写英文，表示主要改动模块。
- 冒号后保留一个空格。标题用中文说明**做了什么**，保持简短、具体，不加句号。
- 一个提交涉及多个模块时，选主要模块作为 `scope`；确实没有单一主要模块时省略 `scope`，不拼接多个模块名。
- 标题避免“更新代码”“优化一下”“继续开发”“修复问题”等无法从历史中辨认改动的描述。

### 类型

| `type` | 使用时机 |
| --- | --- |
| `feat` | 增加用户或业务可感知的能力 |
| `fix` | 修复已存在的错误行为 |
| `refactor` | 调整代码结构，预期行为不变 |
| `docs` | 只修改文档或规范 |
| `test` | 只增加或调整测试 |
| `build` | 修改构建配置或依赖 |
| `ci` | 修改持续集成配置 |
| `chore` | 不属于以上类型的日常维护，例如整理开发脚本 |

功能与测试同时提交时，按功能选择 `feat` 或 `fix`；文档随功能同步更新时，也按功能选择类型。不因为一个提交包含测试或文档就拆成无意义的独立提交。

### 范围

优先使用仓库中稳定的职责名，例如 `policy`、`decision`、`orchestrator`、`liteflow`、`web`、`common`、`db`、`standards`、`deps`。`scope` 随实际代码归属选择；无需为每个新子包增加一种写法。

示例：

```text
feat(policy): 支持按场景发布流程版本
fix(policy): 发布失败时保留原版本指针
refactor(common): 统一接口响应与异常处理
docs(standards): 约定提交标题与拆分方式
build(deps): 引入 Lombok 依赖
```

## 2. 提交内容与正文

- 一个提交对应一个可独立解释的改动。把功能、对应测试和必要文档放在同一提交；无关改动分开提交。
- 提交前检查暂存区，只纳入本次改动。其他人的暂存内容、本地环境配置和 IDE 文件不顺手带入。
- 标题说明结果；当原因、兼容影响或迁移要求仅靠标题看不出来时，空一行写正文。正文说明**为什么这样改**以及需要关注的影响，不逐文件复述差异。
- 对外接口或数据契约出现不兼容变更时，在标题的类型或范围后加 `!`，并在正文使用 `BREAKING CHANGE:` 说明迁移方式。

示例：

```text
refactor(common)!: 统一接口响应结构

前端统一从 data 字段读取业务结果，错误码由全局异常处理器生成。

BREAKING CHANGE: 原接口直接返回的业务对象改为放在 data 字段中；调用方需更新响应解析。
```

## 3. 提交前检查

1. 查看 `git diff --cached --stat` 和 `git diff --cached`，确认暂存内容只属于本次提交。
2. 运行与改动相关的编译或测试；失败时在提交前修正。
3. 再写标题，确保类型、范围与实际改动一致。复杂改动按第 2 节补充正文。

本规范只约束后续提交，不重写已经推送到 `master` 的历史；整理旧历史如有必要，应另行讨论。
