# 前后端协作与接口交接规范

状态：已确认的项目约定。适用于后台页面、业务接口及后续前后端联调。

## 1. 一次先确定一侧

- 一个功能开始前，明确本轮由前端还是后端先行。默认后端先行：先完成业务接口和接口文档，再由前端接入。
- 前端先行适用于交互尚需验证的页面：前端先确定页面行为和所需数据，使用明确标识的模拟数据验证；随后形成接口需求，后端确认并实现契约，前端最后接入真实接口。
- 同一轮不要让前后端在未确定接口契约时各自猜测字段并同时改实现。先行一侧形成可审查的结果，另一侧依据已确认的结果改动；联调放在两侧完成之后。
- 用户明确指定实施顺序时，以该顺序为准。已有接口可直接复用时，先核对文档与实现一致，再接入页面。

## 2. 后端先行的交付物

后端提供接口时，同步维护 `docs/api/<领域>.md`，并在前端开始对接前核对文档与当前代码一致。接口文档至少包含：

1. 用途、方法与路径；路径、查询和请求体参数的名称、类型、必填性、默认值与取值限制。
2. 成功响应的结构和可运行的请求／响应示例；明确 `null`、空列表、枚举、时间、分页和版本号的语义。
3. 失败的 HTTP 状态、稳定 `code`、`data` 形态，以及并发冲突和资源不存在时的行为。
4. 会改变业务状态的接口所需前置条件、修改范围及重复调用行为；草稿修订号、发布指针等并发条件必须说明。
5. 与原接口的兼容关系、当前已实现范围、尚缺少的接口，以及可用于联调的最小调用顺序。

文档中的字段名、状态码和示例以实际 Controller、Req、Resp、`ApiResponse<T>` 和相关测试为准。接口尚未实现时标为“草案”，不要写成已可调用。后端改动契约时，同步更新文档，并明确告知前端变化点。

## 3. 前端先行的交付物

前端先行时，先记录页面操作、加载和错误状态、字段含义及预期请求时机，再给出所需接口的草案。模拟数据与草案字段不得被当作后端已承诺的正式契约；后端确认后，以正式接口文档更新前端类型和请求服务。

前端接入时统一通过 `web/src/services/` 调用接口并解包 `ApiResponse<T>`；页面不自行猜测响应字段。后台列表遵循[分页约定](admin-list-pagination.md)。若文档缺字段或行为含糊，先补齐契约再修改另一侧。

## 4. 交接与联调

| 阶段 | 完成标志 |
| --- | --- |
| 先行侧完成 | 页面行为稿或后端接口及文档已可审查，关键示例与失败场景清楚。 |
| 契约确认 | 双方使用同一份字段、状态和版本语义；未定事项单独标出。 |
| 后行侧接入 | 类型、请求封装和页面状态与已确认契约一致；变更不靠临时硬编码适配。 |
| 真实联调 | 用实际服务完成至少一条成功链路和一条关键失败链路，并记录发现的契约偏差。 |

接口文档记录技术交互；产品目标与迭代范围仍记录在 `prd/`，不把接口字段清单代替 PRD。
