# 后台可配置规则集与规则组件设计

日期：2026-10-15  
状态：已确认并实施的第一版设计；实际交付与限制以接口及演示文档为准。

## 1. 目标与边界

让策略人员在后台编辑、测试并发布一套有版本的规则，流程通过通用“执行规则集”组件引用该版本。第一条贯通用例是结算优惠资格：修改订单门槛、利润底线或预算约束后，可以在后台测试、发布规则，并由新版流程使用，不必为每条规则编写 Java 组件。

本轮规则集是**纯计算**：读取一次决策中已提供的强类型输入，返回一个业务判断及原因；不直接查询 HTTP、RPC 或数据库，不发券，不修改外部状态。数据来源继续由变量中心或调用方负责，流程负责把值映射给规则组件。规则集不接收任意脚本、SQL、Java 类名或 URL。

## 2. 平台对象与菜单归属

| 对象 | 职责 | 管理位置 |
| --- | --- | --- |
| 规则组件 | 通用的“执行规则集”执行器及输入、输出契约 | 组件管理 → 规则组件；能力目录 |
| 规则集 | 一组有序条件行、输出和兜底结果 | 规则中心；独立业务资产 |
| 规则集草稿 | 可编辑的规则内容及草稿修订号 | 规则中心 |
| 规则集版本 | 发布后不可变的规则快照 | 规则中心 |
| 流程节点 | 选择规则集版本并配置输入映射 | 流程资产画布 |

规则集与流程、变量一样有独立业务标识和版本。组件目录只注册一种通用执行能力，不为每套规则新增一个组件。`START`、`RESULT`、`SUBFLOW` 等结构节点继续由流程平台管理。

## 3. 规则表语义

一个规则集声明输入字段的名称和类型，以及允许返回的结果码；类型沿用 `STRING`、`BOOLEAN`、`DECIMAL`。每一行有稳定行标识、优先级、一个或多个条件、结果码、原因码和可读原因。同行条件按 `AND` 组合；按优先级升序检查规则行，**命中第一行立即返回**。优先级不得重复。必须配置兜底结果；没有规则行命中时返回兜底。规则行和兜底只能使用本规则集声明的结果码。结果码是业务文本枚举，例如 `ELIGIBLE`、`INELIGIBLE`，不是执行状态。

第一版操作符：三种类型均支持 `EQ`、`NE`；`DECIMAL` 另支持 `GT`、`GTE`、`LT`、`LTE`。比较常量必须与输入字段类型一致，金额使用十进制精确比较。条件字段只可引用规则集声明的输入；不支持跨行依赖、表达式、嵌套 `OR` 或循环。复杂条件可拆成多行并按优先级排序。

`DECIMAL` 在 API 可用 JSON 数字或十进制字符串输入；服务端按 `BigDecimal` 处理小数，返回给浏览器的比较常量统一为十进制字符串。后台表单和试算框使用字符串保存小数，避免 JavaScript 浮点数在规则保存前丢失精度。

示意规则表：

| 优先级 | 同行条件 | 结果码 | 原因码 |
| ---: | --- | --- | --- |
| 10 | `orderAmount LT 100` | `INELIGIBLE` | `ORDER_BELOW_THRESHOLD` |
| 20 | `marginAfterMaxOffer LT 10` | `INELIGIBLE` | `MARGIN_BELOW_FLOOR` |
| 30 | `remainingBudget LT 18` | `INELIGIBLE` | `BUDGET_INSUFFICIENT` |
| 兜底 | 前述规则均未命中 | `ELIGIBLE` | `QUALIFIED` |

这些金额只属于营销样板。规则中心不内置“优惠”概念；另一个规则集可以声明不同输入和输出码。第一版规则执行结果固定包含 `resultCode`、`reasonCode`、`reason`、`matchedRuleId`、`ruleSetCode` 和 `ruleVersionId`。兜底命中时 `matchedRuleId` 为 `null`。缺失输入、类型不符或规则版本加载失败是**执行失败**，不得返回兜底业务结果。

## 4. 编辑、测试与发布

规则中心提供列表、详情、创建、编辑草稿、试算和发布。列表遵循后台分页约定。草稿保存使用修订号防止覆盖；发布先验证字段、操作符、行优先级、结果和兜底配置，再创建不可变版本并切换该规则集的当前发布指针。验证失败不改变发布指针。已发布版本始终可以按版本 ID 查询，用于追溯旧决策。

试算指定草稿或已发布版本及一组模拟输入，返回匹配行、结果和原因，并指出缺字段或类型错误；试算不发布、不修改业务状态。页面至少让用户看到规则行顺序、兜底结果、输入样例和试算结果。第一版不加入审批流和复杂表达式编辑器。

## 5. 流程集成与版本固定

新增通用 `execute-rule-set` 组件，作为普通 `COMPONENT` 节点执行。节点配置选择 `ruleSetCode`、`ruleVersionId`，并把规则输入逐项映射到流程请求字段或已执行节点的强类型结果。规则组件自身只执行已发布版本，不负责取数。

流程草稿选择规则集的**当前已发布版本**；发布流程时核对该版本仍是规则集当前发布版本、全部输入映射存在，并校验“获取变量”节点来源的类型相容，然后把具体版本 ID 固定在不可变流程版本中。当前流程请求输入只声明字段名、没有类型，来自请求的映射在发布时只能校验字段已声明，实际值类型在试运行与正式执行时严格校验；后续若为流程输入增加类型声明，再前移这部分校验。若规则集在草稿选定后更新，须重新选择并校验。已发布流程始终使用原版本，不随规则集发布自动变化。这与变量和子流程的引用语义保持一致。

规则节点输出结构化结果。下游条件节点使用专门的“规则结果等于指定码”判断能力读取 `resultCode`，且预期码必须属于该规则集声明的结果码；`RESULT` 节点仍负责形成最终业务结论。规则集返回 `INELIGIBLE` 是正常业务结果，规则执行异常则使本次流程失败，不进入业务 `false` 分支。发布校验核对规则节点可达性和结果码，画布不依赖任意 JSON 路径和字符串猜测。

## 6. 营销样板迁移

当前模拟结算服务先计算 `eligible`，资格子流程仅判断该布尔值。这无法证明规则中心能力。迁移后，模拟结算服务提供订单金额、优惠前毛利和当前活动预算使用情况等事实输入；预算累计仍由模拟服务从反馈状态计算，因为规则集不维护状态。第一版由样板的准备层按固定券额计算 `marginAfterMaxOffer`、`remainingBudget` 等数值，再交给资格规则集；调整券额仍需修改样板配置，规则中心只负责可配置的比较门槛。这是第一版计算能力的明确限制。资格子流程运行固定版本的规则集，读取其 `resultCode` 与原因，返回 `ELIGIBLE` 或 `INELIGIBLE`；优惠选择子流程及外层流程继续使用资格结果。

样板初始化可以创建并发布固定规则集，随后发布引用它的资格流程和外层流程。规则集更新后，需重新选择其版本、发布资格流程，再更新引用它的外层流程版本；既有实验和决策保留原规则与流程版本。固定 30 人样本结果在同一规则版本下应保持可重复。样板预算口径目前包含已有优惠，与“新增券预算”的业务定义存在差异；迁移时需明确调整为新增券实际使用额，或在样板中继续标明差异，不应由规则引擎隐式改口径。

## 7. 验收场景

1. 后台创建营销资格规则集，配置三条拒绝规则和兜底通过规则；用四组输入试算，得到对应结果码、原因码和命中行。
2. 发布规则版本，画布选择该版本并映射输入；流程校验、发布和执行成功，决策轨迹能定位规则集版本及命中行。
3. 修改草稿门槛并发布新版规则；原已发布流程继续使用旧版。重新选择、发布资格流程及外层流程后，新决策才使用新版。
4. 缺失输入或类型错误导致明确执行失败；业务拒绝仍是正常结果，不混淆两者。
5. 营销固定样本在同一组规则及流程版本下保持原有支付、优惠和利润计算结果；反馈链路不由规则组件执行。

## 8. 实施顺序

遵循前后端接口交接规范，先实现规则集后端模型、验证、试算、版本发布和 `docs/api/` 契约；随后接入规则中心页面；再接入 `execute-rule-set` 与流程发布校验、画布配置；最后迁移营销样板并联调。每一阶段均以真实接口和样板输入验证，前端不自行猜测规则执行响应。
