# 场景与可视化流程模型设计

日期：2026-10-12
状态：待审阅

## 目标与边界

建立场景码、流程版本、可复用组件和流程节点之间的关系，让 X6 绘制的流程在校验后交给 LiteFlow 执行。当前仓库已分别接入 LiteFlow 固定示例链与 X6 示例画布；本设计是两者打通的依据。

首个实施切片只处理**同步执行的结构化流程**：串行、等待全部分支完成的并行、条件分支和显式汇合。画布可保存更一般的节点与边，但不能转换的图不得发布。异步请求入口、灰度、影子运行、复杂组件目录和业务规则内容属于后续切片；它们复用本设计的场景与版本边界。

## 领域关系

```text
Scene(sceneCode)
  └── publishedVersionId → FlowVersion
                               ├── GraphDefinition(nodes, edges)
                               ├── compiledChainId
                               └── compiledEL

GraphNode(component instance) ──componentKey──→ ComponentDefinition / Executor
```

- **场景**是业务调用方识别决策流程的稳定标识。一个场景在同一运行环境中指向一个当前已发布流程版本。
- **流程版本**是不可变快照。它保存经校验的图、编译后的 LiteFlow chain ID 与 EL，以及所引用组件的版本或配置快照。修改流程产生新版本，不原地修改已发布版本。
- **组件定义**描述可复用的执行能力，例如 HTTP 调用、查库、规则计算。组件的输入输出契约独立于任何单条流程。
- **流程节点**是组件在某个流程中的一次使用，拥有独立节点 ID、参数映射、超时和失败策略。一个组件可被多个节点引用。
- **编排节点**描述控制结构：并行拆分、并行汇合、条件判断、条件汇合。它们没有业务副作用。
- **连线**描述先后关系；条件分支的出线携带 `true` 或 `false` 标签。画布坐标仅用于编辑，不参与运行语义。

## 图数据契约

前后端交换独立于 X6 内部序列化格式的 `GraphDefinition`。X6 的节点与边由前端适配成以下语义数据；布局单独保存，不能决定执行顺序。

```json
{
  "schemaVersion": 1,
  "nodes": [
    {"id": "start", "kind": "START"},
    {"id": "lookup", "kind": "COMPONENT", "componentKey": "query-profile", "failurePolicy": "FAIL_FAST", "config": {}},
    {"id": "end", "kind": "END"}
  ],
  "edges": [
    {"id": "e1", "source": "start", "target": "lookup"},
    {"id": "e2", "source": "lookup", "target": "end"}
  ],
  "layout": {
    "start": {"x": 80, "y": 120},
    "lookup": {"x": 280, "y": 120},
    "end": {"x": 480, "y": 120}
  }
}
```

`config` 为节点实例配置，由所引用组件的配置模式校验；它不能任意指定 Java 类名或执行代码。节点 ID 和边 ID 在单个流程版本内唯一。组件引用在发布时解析为确定的组件实现与配置版本。

首个实施切片只支持 `FAIL_FAST`：组件失败即终止流程并返回执行错误。`SKIP`、兜底结果和重试等策略需要结合首个业务场景另行设计，不能在首期配置中使用。

## 支持的控制结构

1. 每张可发布图恰有一个 `START` 和一个 `END`；所有节点必须从起点可达且能到达终点。
2. 普通组件节点恰有一条入线和一条出线；起点只有出线，终点只有入线。
3. `PARALLEL_SPLIT` 有至少两条无标签出线，分别进入并行分支；对应的 `PARALLEL_JOIN` 等待所有分支结束后继续。每条分支只能在这个汇合节点结束，不能跨接其他分支。汇合后的节点执行一次。
4. `CONDITION` 有且只有 `true`、`false` 两条出线；两条分支在对应的 `CONDITION_JOIN` 汇合。只执行命中的分支，随后继续执行一次公共后继节点。
5. 并行和条件结构可以嵌套，不能交叉重叠。首期不支持回边、循环、任意共享子图、多入口子图或跨分支连线。
6. 每个节点的执行参数来自本次请求和上游节点结果。并行分支各自写入独立的节点结果空间；汇合后统一读取，避免并发写同一个字段。

这些约束使可发布图能够还原为确定的嵌套结构。X6 仍允许编辑一般图；保存草稿不代表该图可执行。

## 转换与运行

发布时由后端完成：结构校验 → 组件引用及配置校验 → 构建嵌套编排树 → 生成 LiteFlow EL → 验证生成的 chain 能加载和执行预置样例 → 固化流程版本 → 将场景的发布指针切换到该版本。发布指针切换必须是原子操作；运行中的请求继续使用已选定的旧版本。

新版本加载成功后才切换指针；运行时保留旧版本 chain，直到使用它的请求结束。发布失败时指针保持原值，不出现指向未加载 chain 的状态。

转换示例：

```text
START → prepare → PARALLEL_SPLIT ┬→ queryProfile ─┬→ PARALLEL_JOIN → decide → END
                                └→ queryDevice  ──┘

THEN(prepare, WHEN(queryProfile, queryDevice), decide)
```

`PARALLEL_JOIN` 是图语义节点，不生成业务组件；`WHEN` 完成所有分支后，后续的 `decide` 执行一次。生成的 chain ID 包含流程版本，流程节点 ID 与组件 key 分开保存；节点调用的适配方式需在实施时用 LiteFlow 验证，保证同一组件可多次引用且配置互不串扰。LiteFlow 负责执行可表达的链；场景选择、版本固定、发布校验和结果封装由平台负责。

同步请求携带 `sceneCode` 和场景输入。入口选择当前发布版本，将其 ID 固定在本次执行上下文，再运行对应 chain，返回流程执行状态、组件输出与节点轨迹。业务决策值由场景内的决策组件产生，其枚举和聚合规则在首个业务场景设计中确定。未找到场景或发布版本时返回明确错误，不执行默认场景。将来异步入口先保存请求和已选版本 ID，再由后台运行相同执行服务。

## 校验与错误处理

- 草稿保存可接受尚未完成的图，但必须满足 JSON 结构、标识唯一性和数据大小限制。
- 发布校验拒绝成环、孤立节点、缺少或重复的分支标签、不匹配的拆分与汇合、跨分支连线、不可用组件、无效节点配置，以及无法生成 LiteFlow EL 的图。
- 校验错误返回稳定错误码、节点或边 ID、可读说明，供 X6 定位问题。
- 组件执行失败按节点失败策略处理；首期仅接受 `FAIL_FAST`。业务决策值语义在首个业务场景设计中确定。未定义策略的节点不能发布。
- 执行轨迹至少记录请求 ID、场景码、流程版本、节点 ID、开始和结束时间、执行状态及错误码；敏感输入不直接写入轨迹。

## 存储与包职责

- MySQL 保存场景、草稿、不可变流程版本、发布指针和审计索引。Redis 可用于运行时缓存，但 MySQL 的发布指针是持久事实来源。
- `policy` 管理场景及发布版本；`orchestrator` 管理图校验、转换、LiteFlow 适配与执行；`component` 管理组件定义和执行适配；`decision` 管理同步请求和结果；`audit` 管理执行轨迹。
- 首期保持单 Maven 模块和 `web/` 前端目录，以包和接口隔离职责。是否拆 Maven 模块由实际依赖边界和部署需求决定。

## 首个实施切片的验收

1. X6 能编辑并提交上述结构化图，后端能返回定位到节点或边的校验结果。
2. 后端能把串行、并行、条件与汇合图转换为 LiteFlow EL；每类结构有成功与拒绝样例。
3. 一个示例场景能发布不可变流程版本，并由同步请求选中该版本运行，返回流程执行状态与节点输出。
4. 并行汇合后的公共节点只执行一次；一次请求从开始到结束使用同一流程版本。
5. 后端测试验证图校验、EL 转换、版本固定和示例执行；前端构建及浏览器操作验证图编辑与错误定位。
