# 决策子流程引用与执行设计

日期：2026-10-14
状态：已确认并实施；本文覆盖原任务 T3 的引用与版本固定，以及使其可发布、可运行所必需的 T4 后端执行。验收以代码与测试为准。

## 目标与范围

外层决策流程通过独立 `SUBFLOW` 节点调用已发布的决策流程。一次外层运行可以包含多个调用节点；每个节点只接收显式映射的输入，并把子流程结果存放在自己的节点 ID 下。外层最终业务结果继续由外层 `RESULT` 节点决定。发布外层版本时固定子流程版本 ID，此后子流程再发布不会改变外层行为。

本设计以 [v0.1 PRD](../../../prd/iterations/2026-10-v0.1-decision-subflow/prd.md) 和 [营销样板](../../../prd/scenarios/checkout-offer-incremental-profit.md) 为依据。独立流程的页面选择器、画布配置、决策详情页面和模拟订单反馈分别在后续前端及样板任务接入。由于当前发布过程会加载并试运行链，子流程引用的校验、固定和执行须在同一后端切片交付，不产生已发布但不能执行的版本。

## 当前代码约束

- `tb_flow_version.graph_json` 保存不可变流程图，`FlowVersion` 带版本 ID、版本号、图和编译后的 EL；`FlowAssetRepository#findVersion(id)` 可读取指定版本。
- `tb_flow.published_version_id` 表示当前发布版本。版本表未记录“曾发布成功”的独立状态，发布失败的候选版本也可能留在表中。因此本轮只允许草稿选择**子流程当前发布版本**；外层发布前再次核对其 ID。历史版本选择需另行补发布状态契约。
- 现有图只支持 `START`、`END`、`COMPONENT`、`CONDITION`、`RESULT` 及结构化分支。`RESULT` 运行时写入单次执行结果槽；`DecisionExecutionService` 仍按场景选择外层入口版本。
- `FlowPublicationServiceImpl` 和 `FlowAssetServiceImpl` 都会校验、编译、保存版本、加载链并用示例输入试运行，然后切换发布指针。两条路径都要使用相同的子流程规则。
- 当前条件组件只读请求输入。要根据子流程结果选择外层结论，需要给条件节点增加明确的结果来源配置，不能让子流程直接修改外层请求输入。

## 引用节点契约

新增 `NodeKind.SUBFLOW`，一入一出，失败策略固定为 `FAIL_FAST`，`componentKey=null`。示例配置如下；字段名是拟议接口，代码实现及 `docs/api/` 核对后才成为正式契约。

```json
{
  "id": "eligibilityCall",
  "kind": "SUBFLOW",
  "componentKey": null,
  "failurePolicy": "FAIL_FAST",
  "config": {
    "flowCode": "offerEligibility",
    "versionId": 41,
    "inputMappings": {
      "userId": { "source": "REQUEST_INPUT", "key": "userId" },
      "orderAmount": { "source": "REQUEST_INPUT", "key": "orderAmount" },
      "priorConclusion": { "source": "NODE_RESULT", "nodeId": "priorCall", "path": "businessResult.conclusion" }
    }
  }
}
```

`versionId` 是子流程发布版本的数据库 ID，不是版本号或 LiteFlow chain ID。画布选择子流程时读取其当前 `publishedVersionId` 并写入草稿；保存草稿不自动更新版本。`inputMappings` 的键是子流程输入字段名，值是唯一来源：外层请求输入的字段，或已执行上游节点的结果字段。映射不允许“传递整个外层上下文”；缺少配置、来源不存在、字段解析失败均要给出可定位错误或运行失败。结果路径先支持对象字段的显式点路径，不执行表达式或脚本，不读取数组下标。

本轮新增最小的流程输入声明，供发布时核对映射完整性：被引用流程在独立资产上声明必需输入字段名集合；外层调用节点必须对每个必需字段配置映射，额外传入字段在发布时拒绝。流程声明随不可变发布版本固化，不能只读取后续可变资产元数据。若保留图 JSON 作为唯一快照，可在图顶层增加 `requiredInputs`；图 schema 版本与旧图兼容方式需在实施计划中明确。该声明只描述字段名和必填性；更细的 JSON 类型、范围及业务校验由后续样板补齐。

## 发布校验与版本固定

`/validate` 和两种 `/publish` 路径都检查：

1. 节点配置格式、流程码、正整数版本 ID、非空映射目标、合法来源路径。
2. 引用对象存在、为 `DECISION` 流程，所选 `versionId` 与该流程**当前** `publishedVersionId` 相同，且版本记录归属于该流程。不存在或已被更新时返回定位到调用节点的 `SUBFLOW_VERSION_UNAVAILABLE`，让用户重新选择。
3. 子流程图不含 `SUBFLOW`，只允许“外层 → 子流程”一层；不能引用自身或通过子流程形成循环。错误分别定位为 `SUBFLOW_NESTING_UNSUPPORTED`、`SUBFLOW_CYCLE`。
4. 输入映射覆盖子流程版本声明的必需字段，且来源节点在每条到达调用节点的路径上均已执行；并行结构下只能引用汇合后确定可用的结果。错误定位为 `SUBFLOW_INPUT_MAPPING_INVALID`。同一子流程可以在外层出现多次，使用不同节点 ID 和映射。
5. 外层仍通过 T2 的每条路径恰好一个 `RESULT` 校验，子流程自己的业务结果不计作外层最终结果。

通过校验的 `SUBFLOW.config.versionId` 直接保存在外层不可变 `graph_json` 中。切换外层发布指针时，在同一数据库事务内按流程码顺序锁定所引用的子流程资产行，并再次核对每条当前发布指针；若子流程已经切换，新外层版本不得成为当前发布版本。若外层先取得锁并完成发布，子流程随后发布新版本不影响外层已固定的版本 ID。这里固定的是引用版本 ID，不依赖子流程当前发布指针的运行时值。

外层发布时校验子流程引用和输入映射，加载编译后的外层链；包含 `SUBFLOW` 的图不做演示输入试运行，因为仅有必需字段名不能构造通用的合法业务值。已有无子流程图保留原试运行检查。真实运行能力由独立的端到端集成测试验证，发布成功不等于所有未来业务输入都能运行成功。

## 运行时数据隔离

`SUBFLOW` 编译为 LiteFlow 专用适配节点，内部通过公开的组件服务执行固定 `FlowVersion`；业务层不能直接操作 LiteFlow 注册表或上下文。每次调用为子流程创建新的执行上下文，输入对象仅包含 `inputMappings` 得到的字段，结果槽、节点结果和轨迹均独立于外层；请求关联标识保留外层请求 ID 和调用节点 ID，便于追溯。每个子调用的实际版本 ID、状态、业务结论、原因和明细作为结构化结果放入外层 `nodeResults[调用节点ID]`，不会写入其他节点 ID 或覆盖外层 `businessResult`。

条件节点可显式选择 `REQUEST_INPUT` 或 `NODE_RESULT` 作为判断来源，例如读取 `eligibilityCall.businessResult.conclusion`。原有 `inputKey` 配置继续按请求输入读取，保持旧发布版本运行行为；新的来源形式在前后端契约中单独说明。条件比较运算本轮先定义有限的字符串相等和布尔判定，避免把营销规则表达成任意脚本。外层的 `RESULT` 仍使用 T2 的静态配置；需要把子流程动态明细复制到外层结果时，再通过受控映射扩展，不在本轮偷偷引用节点私有 JSON。

子流程失败或未返回业务结果时，`SUBFLOW` 节点按 `FAIL_FAST` 终止外层：外层 `status=FAILED`、`businessResult=null`，保留调用节点和子流程版本的失败位置；子流程已开始执行时，失败节点轨迹保存在该调用节点结果的 `childTrace`。成功返回“无优惠”“拒绝”之类业务结论不算运行失败，外层可以继续执行并自行决定最终结果。运行时对缺少映射值、指定版本不可读、旧子流程版本没有结果等情况返回稳定错误码，不自动改用子流程新版本。

## 存储、启动恢复与接口

优先复用 `tb_flow_version.graph_json` 固定引用，不为外层版本另建引用表。子流程版本从外层图中收集；应用启动时除当前发布指针指向的链，还要加载这些外层版本**固定引用**的子流程链。进程内如缺少某条固定链，执行前按版本 ID 从数据库加载其不可变 EL。引用版本即使不再是子流程当前发布版本，也须可供已发布外层版本使用。

后端完成后维护 `docs/api/flow-assets.md` 和 `docs/api/decision-results.md`：节点 JSON、校验错误、版本 ID 语义、输入映射、结果嵌套、失败形态及最小调用顺序均以 Controller、Req/Resp 和集成测试为准。前端通过 `web/src/services/` 读取流程资产与版本信息，再接入画布；现有演示流程无需因新增节点类型改变结果含义。

## 验收案例

- 独立发布资格与选择两个子流程；同一外层流程调用两者，结果分别位于两个调用节点下，外层 `RESULT` 产出的最终结论可与子流程结论不同。
- 两个调用节点引用同一子流程、映射不同输入时，子流程各自只收到映射后的字段，输出互不覆盖。
- 子流程从 v1 发布到 v2 后，已发布外层版本继续使用 v1；重新选择并发布外层新版本后才使用 v2。重启后同样成立。
- 未发布流程、引用版本与流程码不匹配、发布前更新、输入映射缺失、超过一层嵌套、循环引用均阻止发布且保持外层旧指针。
- 子流程运行失败时外层失败、无正常业务结果，能从调用节点定位子流程及版本；正常业务上的“不新增优惠”仍为成功。

## 实施前需确认的选择

本设计采用“草稿只选当前发布版本、发布后固定版本 ID”的路线。历史发布版本直接选择需要可靠的发布状态记录和相应迁移；当前表无法区分历史成功版本与未发布候选，因此不把它作为本轮能力。若希望在外层草稿中长期保留旧版本选择，需要先增加版本发布状态契约。
